# Backend

- `app/main.py` initializes SQLite through the FastAPI lifespan, installs API routers and browser-write checks, then serves the static frontend. Keep API routes ahead of the static mount. The fallback checks registered router definitions: unknown API paths return JSON 404, while known paths with unsupported methods return JSON 405 and the correct `Allow` header. FastAPI stores included-router wrappers in `app.routes`; do not assume it directly contains every endpoint.
- `app/auth.py` accepts the MVP credentials and resolves the user ID from SQLite. Opaque HttpOnly/SameSite=Strict sessions stay in `app.state.sessions`, expire after eight hours, and are revoked on logout or server restart.
- `app/database.py` implements the approved design in `../docs/DATABASE.md`: two SQLite tables, one JSON board per user, seed-once initialization, short-lived connections, and atomic revision checks. Use `DATABASE_PATH` or the default `backend/data/kanban.db`. Never reseed an existing row, even if empty or invalid. Package the exact approved dummy board in `app/seed.json`.
- `app/models.py` owns strict board validation. Its nonblank regex matches complete strings (including newlines), preserving server rules while avoiding provider decoders interpreting an unanchored pattern as a single character. `app/boards.py` exposes authenticated GET/PUT `/api/board`. AI changes reuse this validation/storage path; stale revisions return 409 without saving.
- Protect private routes with `Annotated[Session, Depends(require_session)]` and derive ownership from `session.user.id`. Never accept a client-supplied identity as authorization. Keep private responses uncached.
- Frontend persistence was completed in Part 7. `app/chat.py` exposes authenticated POST `/api/chat` with `{message, history?}` -> `{reply, updated, revision, board}`. History allows only user/assistant roles and stays request-local. Load the owner's authoritative board before the provider call, with its connection closed. Use one initial system policy message, then supplied user/assistant history, then the current authoritative board and latest question together in the final user message. This keeps current state after historical requests and avoids multiple-system-message serving-template incompatibilities. The prompt limits execution to the latest request and preserves existing card identity when moving/editing. Validate `AIResult` (reply and nullable complete board), then save against the original revision. Reply-only requests reread current saved state without writing. Return a reply only after a successful save; stale candidates return 409. Part 10's sidebar applies this saved response. Never persist chat in SQLite or sessions.
- `app/openrouter.py` calls OpenRouter with standard-library HTTP/JSON, hardcoded model `openai/gpt-oss-120b`, a 45-second network timeout, and an 8,192-token completion budget for full-board replies, and temperature zero to reduce sampling variation. Request strict JSON Schema with `provider.require_parameters: true`; validate output locally as well. Read `OPENROUTER_API_KEY` at call time; missing configuration returns 503 without preventing startup or board use. Return concise sanitized errors; never log headers, keys, request bodies, or provider payloads. No startup calls, automatic retries, model fallback, or paid calls in the default test suite.
- The user explicitly chose real OpenRouter verification without mocked provider responses. Local route/auth/validation/missing-configuration tests make no provider request. Live checks are explicit and should be recorded separately from local test results.
- `uv run --locked --env-file ../.env pytest tests/live_chat.py -W error` runs explicit paid checks against the real provider using isolated app/database fixtures. The file is deliberately excluded from default discovery. No provider-response mocks, real-user board resets, or credential output.
- Run `uv run --locked pytest -W error` from this directory. Tests use isolated databases outside their static-file directories. Follow the root's practical 80% testing policy; prioritize authentication and data boundaries over percentage-driven tests.
