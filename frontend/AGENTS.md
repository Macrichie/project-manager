## Existing frontend

- This directory contains the client-rendered Next.js App Router app. Read `../AGENTS.md` and `../docs/PLAN.md` before changes. The plan and database design are approved; follow the recorded phase progress.
- `app/page.tsx` renders `AuthGate` from `app/auth.tsx` and mounts `ProjectBoard` only after server authentication. `auth.tsx` handles sign-in, session restoration/expiry, focus revalidation, and sign-out; tokens stay in an HttpOnly cookie, with no browser storage.
- `app/board-view.tsx` defines the board, column/card components, and a shared inline add/edit form. Form text stays open on save failures; successful saves close forms and restore focus. Pointer targeting follows the pointer location; keyboard arrows follow card/column order so the rotated overlay does not misdirect navigation. Unmounting discards local drafts and drag state.
- `app/board.ts` defines `Card` and `Column`, seeds ten cards in five columns, and exports `moveCard`. Its optional destination index supports immutable reordering within a column and insertion between columns.
- `app/use-board.ts` loads the authenticated board and saves full documents with the current revision. Render the server response after success, permit one save at a time, and reload after failure/conflict before allowing another write. Failed recovery blocks changes until reload succeeds. Never automatically resubmit stale data. Abort in-flight reads/writes on unmount and handle API 401 through the sign-out callback.
- The same hook coordinates `/api/chat` with manual saves using one synchronous request lock. Apply returned saved board/revision before appending a successful user/assistant pair. Keep confirmed messages and a pending message in React memory only; failed requests retain composer text but add no successful history. Refetch after chat failures because a lost response may follow a committed change. Never automatically retry the model or persist chat to browser storage.
- Existing features: column renaming, adding/editing/deleting cards, and moving/reordering cards through dnd-kit pointer and keyboard sensors. Cards use `useSortable` inside one `SortableContext` per column; the drag overlay is presentational. Saved data survives refresh, logout/login, and restart.
- Authentication uses the FastAPI `/api/auth/login`, `/api/auth/me`, and `/api/auth/logout` endpoints; private board data uses GET/PUT `/api/board`. `app/chat-panel.tsx` renders the live assistant, opened by the toolbar button. Keep it mounted when closed so page-local drafts/history survive toggling; AuthGate unmount clears them on logout, expiry, or authentication loss. Enter sends, Shift+Enter inserts a newline, and Escape/close restores toggle focus.
- `app/globals.css` supplies the existing visual design and responsive board layout; its `chat.css` import styles the assistant as a desktop sidebar and a panel above the board on small screens. Keep board overflow inside its scroll area. `app/layout.tsx` supplies the root layout; `public/` contains static assets.
- Dependencies include React, TypeScript, `@dnd-kit/core`, `@dnd-kit/sortable`, `@dnd-kit/utilities`, and `lucide-react`. Preserve the existing design and reuse these tools where suitable.

## Existing verification

- `tests/board.test.ts`: unit coverage for ordering within columns, insertion at specific positions between columns, empty targets, unchanged/invalid moves, and preservation of unrelated data.
- `tests/page.test.tsx`: component coverage for API loading/saving, CRUD, validation/cancellation, pending saves, conflicts, retained drafts, ambiguous network failures/recovery, and authentication loss. `tests/board-api.ts` supplies an isolated mock API. Setup is in `tests/setup.ts`; configuration is in `vitest.config.mts`.
- `tests/chat-panel.test.tsx` checks presentation/composer behavior and parent acceptance callbacks without fabricating provider replies. Board component tests also check chat/manual serialization and transport-failure recovery. Actual replies, board application, and history/session behavior are verified through the real provider in browser tests.
- `tests/auth.test.tsx` covers session gating/restoration, sign-in errors, connectivity recovery, logout failure, authentication loss, and expiry. `e2e/auth.spec.ts` verifies the actual browser/server login/logout flow and session revocation. Board browser tests sign in through the server before exercising the board.
- `e2e/board.spec.ts`: persisted workflows, two-tab conflicts, empty boards, pointer dragging/cancel, keyboard focus/movement, mobile touch dragging, and layout captures. `e2e/fixtures.ts` temporarily installs the seed and restores prior board data around serial board/auth tests; use an isolated container/database for integration runs.
- `e2e/restart.spec.ts` explicitly restarts an isolated Docker container and checks browser-made changes survive. It runs only on desktop when `PLAYWRIGHT_RESTART_CONTAINER` names the target container; set `PLAYWRIGHT_BASE_URL` to the same instance. Ordinary runs skip it.
- `e2e/chat.spec.ts` uses `PLAYWRIGHT_LIVE_AI=1` for real-provider conversation, saved multi-card changes/reordering, page-only history, and conflicts with manual saves. `PLAYWRIGHT_NO_AI_URL` selects an isolated unconfigured server for real 503/manual-use checks; a separate network-abort workflow makes no provider call. No model replies are stubbed. Live workflows may explicitly resubmit once after verifying an invalid-output refusal preserved the board/draft; product code never auto-retries.
- `playwright.config.ts` runs desktop and mobile Chromium projects against an isolated development server on port 3100, with one worker and a 60-second per-test budget for cold development-server runs. It refuses to reuse an occupied port; override with `PLAYWRIGHT_PORT`, or set `PLAYWRIGHT_BASE_URL` to test an already running deployment. The launch command supports Windows and Unix.
- `playwright.scaffold.config.ts` and `e2e-scaffold/` test the deployed board, asset loading, API boundaries, API documentation, and health/hello aliases on port 8000 by default, or `PLAYWRIGHT_BASE_URL`. Run `npx playwright test --config playwright.scaffold.config.ts`.
- Run from `frontend/`: `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`, and `npm run test:e2e` (requires Playwright Chromium).
- `npm run dev` launches the development server and proxies `/api/*` to the running FastAPI backend on port 8000. Production `npm run build` uses `output: "export"`, producing `out/` without server-only cache/prefetch or proxy settings. The Docker Node build stage copies this export into the Python image; production runs FastAPI without a Next.js runtime server.
- Test files describe intended checks; consult recorded run results before claiming they pass. Retain persistence assertions and the practical testing policy.
